# Task: Fix Credit Scoring Input Validation, Credit History Verification, Derived Feature Transparency, and Applicant-Facing Explainability

We already have a trained XGBoost repayment-scoring model and an existing SHAP + LLM + PDF explainability pipeline.

**Important: Do NOT retrain the model and do NOT regenerate the dataset. The existing trained model must remain unchanged.**

The goal of this task is to improve the application/input flow and make the explainability genuinely useful and understandable to a normal applicant.

---

## 1. Preserve the Existing Model

Do not modify, retrain, or replace the saved XGBoost model.

Do not change the model's learned behavior.

The model currently expects the existing model features, including:

* age
* occupation
* monthly_income
* existing_loan_history
* debt_to_income_ratio
* loan_size
* telecom_usage_score
* mobile_wallet_activity
* digital_purchase_frequency
* psychometric_score

`loan_history_code` is only a numeric encoding of `existing_loan_history`.

Do NOT pass both `existing_loan_history` and `loan_history_code` to the model.

The model must continue using `existing_loan_history` as the categorical feature.

# 2. Loan Amount Validation Must Happen at the Beginning

The applicant should be told the supported loan amount range when filling out the application.

Based on the current training dataset, the supported loan amount range is approximately:

* Minimum: PKR 50,000
* Maximum: PKR 1,200,000

The generated dataset has a minimum observed loan size of approximately PKR 50,296 and a maximum of PKR 1,200,000.

Implement this as an application-level validation rule.

### UI behavior

When the applicant enters the requested loan amount, show:

> Requested loan amount must be between PKR 50,000 and PKR 1,200,000.

If the entered value is below 50,000 or above 1,200,000:

* Show a clear validation error.
* Do not allow the application to proceed.
* Do not call the ML model.
* Do not calculate SHAP.
* Do not generate the PDF.
* Do not call the LLM.

Example:

> **Loan amount out of range**
> Please enter a loan amount between PKR 50,000 and PKR 1,200,000.

This validation must happen before model inference.

Also remove the old validation range that allowed:

`10,000 – 10,000,000`

The current model must never silently score an unsupported loan amount.

# 7. Deterministic Mapping From Credit Information to Existing Loan History

Do not ask the LLM to decide the loan-history category.

Implement a deterministic Python function.

For example:

```python
def derive_loan_history(credit_data):
    ...
```

The mapping should be documented and deterministic.

Suggested logic:

1. If `has_previous_loan == False` and there is no outstanding debt:
   → `No Previous Loan`

2. If `has_overdue_or_default == True`:
   → `Previous Default`

3. If previous borrowing exists and repayment behavior is consistently on time:
   → `Good Repayment History`

4. If previous borrowing exists but there is evidence of delayed payments without default:
   → `Delayed Repayment History`

The exact implementation should handle inconsistent mock records safely.

For example, if `has_previous_loan == False` but outstanding debt is greater than zero, flag the record as inconsistent rather than silently generating a misleading category.

# 16. SHAP Remains a Technical Explanation Layer

```text

       ↓

       ↓

       ↓

       ↓
```

* calculate the score
* modify the score
* modify SHAP contributions
* reverse positive/negative direction
* invent feature values
* invent data sources
* claim simulated data is real
* decide the loan-history category

* invent formulas
* claim causality


The LLM only verbalizes this information.
